**Спецификация: Scoring Agent в составе мультиагентной системы МСБ**

**0\. Позиционирование**

Это **не самостоятельный сервис**, а логика одного из 5 субагентов, работающая в контуре оркестрации, политик и аудита.

**Ключевое архитектурные решение для ИИ (из АР МСБ §3.1):**

- Агенты **не взаимодействуют напрямую** — все вызовы через Оркестратор (паттерн Оркестрация, выбран в АР Оркестратор, развилка 1)
- ИИ **не принимает финальное финансовое решение** — финальное решение за андеррайтером (для заявок >5 млн ₽) или за Review Agent (для low-risk, R5)
- ИИ выступает как **интерпретатор результатов классической скоринг-модели и агрегированных данных**, а не как замена скоринг-модели

**1\. Действия Scoring Agent**

**1.1 Роль в бизнес-процессе**

_Scoring Agent вызывает скоринг-модель через GenAI-Ready API и интерпретирует результат._

- Скоринг-балл (например, 685/1000)
- Риск-категория
- Риск-факторы с источниками (Real-time Explainability)
- Предварительный вердикт

**1.2 Три категории решений**

| **Категория**     | **Значение**                   | **Что происходит дальше**                                        |
| ----------------- | ------------------------------ | ---------------------------------------------------------------- |
| recommend_approve | Высокая вероятность возврата   | Переход к Compliance Agent → Review Agent → HITL (если триггеры) |
| recommend_review  | Средняя вероятность / аномалия | Эскалация на андеррайтера (сценарий 2 из АР HITL)                |
| recommend_reject  | Низкая вероятность возврата    | Запуск Саги-компенсации (из суб АР Сага) → уведомление клиента   |

**Э**то **рекомендации**, а не решения. Финальное решение — за человеком (для критических заявок) или за Review Agent (для стандартных). Это согласуется с разделом 1.3 АР МСБ: _«Все финансовые транзакции требуют human-in-the-loop (R1)»_.

**2\. Интеграция с другими агентами (входные данные)**

**Каждый агент получает изолированный context_bundle** (принцип Mixture of Experts из АР МСБ §3.1, п.1). Реальный вход собирается из результатов других агентов:

**2.1 Что поступает в Scoring Agent (через Оркестратор)**

| **Источник**                | **Данные**                                                                    | **Основание в АР**                                          |
| --------------------------- | ----------------------------------------------------------------------------- | ----------------------------------------------------------- |
| **Document Agent**          | Извлечённые данные из PDF/сканов (анкета, фин. отчётность, выписки) через OCR | АР МСБ §2.2, шаг 3a                                         |
| **MCP Gateway → БКИ**       | Кредитная история клиента                                                     | АР МСБ §2.2, интеграции; АР МСБ §5.2 (порт 443, mTLS + JWT) |
| **MCP Gateway → ФНС/ЕГРЮЛ** | Верификация контрагента                                                       | АР МСБ §5.2 (порт 443, mTLS)                                |
| **АБС (GenAI-Ready API)**   | Данные о счетах, обороты                                                      | АР МСБ §2.2, интеграции; АР МСБ §4.2 (доработка АБС)        |

**5\. Интеграция с Policy Hook Bus (обязательная)**

Это **обязательный компонент Архитектуры** (АР МСБ §3.1, п.3: «Все требования 152-ФЗ, ЦБ РФ, OWASP закодированы как OPA Rego policies и enforce через Policy Hook Bus»).

**5.1 До вызова модели (pre-action hook)**

Из потока П05 АР Оркестратор:

Оркестратор → Policy Hook Bus: {

action: "scoring_analysis",

context: {r_level, sandbox_profile, data_sensitivity},

policy_ids: \["152-FZ", "CBR-AML"\]

}

Возможные решения (из потока П06):

- ALLOW — анализ разрешён
- DENY — анализ заблокирован (например, ПДН не локализованы)
- MODIFY — разрешён с модификацией (маскирование ПДН во входе)
- ESCALATE — передача человеку

**5.2 После получения результата (post-action hook)**

Проверка ответа модели:

- Нет ли в ответе ПДН в открытом виде (маскирование)
- Соблюдена ли структура вывода
- Если escalation_required=true → создание Human Task в Temporal

**Это согласуется с АР МСБ §3.1, п.2:** _«Хуки исполняются синхронно, обеспечивая запрет по умолчанию»_ и _«Контроль бюджета»_ (трёхуровневый Cost CB из суб АР).

**6\. Fallback'и**

В нашей архитектуре есть **полноценный механизм** — два типа Circuit Breaker из суб АР. Используем их.

| **Ситуация**                                | **Действие (по суб АР CB)**                                                  | **Основание**                                                                                                      |
| ------------------------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| LLM не вернул валидный JSON после 3 попыток | Переход в recommend_review + эскалация андеррайтеру                          | Суб АР Сага, триггер 2.2.1 (технический сбой); АР Оркестратор §4.1, п.2 (идемпотентность)                          |
| confidence < 0.7                            | recommend_review + эскалация                                                 | Логика исходной спецификации; согласуется с АР МСБ §1.3, п.4                                                       |
| LLM Inference недоступен (3 сбоя за 30 сек) | **Failure CB срабатывает**: остановка сессии, checkpoint, эскалация человеку | Суб АР CB, таблица точек отказа: «LLM Inference (GigaChat / LiteLLM): threshold=3 сбоя за 30 сек, cooldown=60 сек» |
| Превышен бюджет токенов (70%)               | **Soft warning**: алерт в Observability, продолжение работы                  | Суб АР CB: «Soft warning: 70% бюджета»                                                                             |
| Превышен бюджет токенов (100%)              | **Hard stop**: остановка + эскалация человеку                                | Суб АР CB: «Hard stop: 100% бюджета»; поток П08 суб АР                                                             |
| policy_flags содержит 115-FZ или SANCTIONS  | recommend_reject + **запуск Саги-компенсации**                               | Суб АР Сага, триггер 2.2.2 (бизнес-отказ); АР МСБ §3.1                                                             |
| Заявка > 5 млн ₽                            | Обязательная эскалация на андеррайтера                                       | АР МСБ §2.2, шаг 8; АР HITL                                                                                        |

**7\. HITL-триггеры (из АР HITL)**

Когда человек вмешивается в нашей архитектуре **чётко определено** в Decision Map (АР HITL):

| **Точка валидации**     | **Кто валидирует** | **Критерии эскалации**                         | **Что блокирует** |
| ----------------------- | ------------------ | ---------------------------------------------- | ----------------- |
| **Скоринг и одобрение** | Андеррайтер        | Сумма >5 млн ИЛИ Скоринг <600 ИЛИ Выручка -20% | Выдача кредита    |

**Применение в этой спецификации:**

- Если requested_amount > 5_000_000 → escalation_required = true
- Если risk_score < 600 → escalation_required = true
- Если в данных выявлено падение выручки на 20%+ → escalation_required = true
- Эскалация исполняется через **сценарий 1 АР HITL** (HITL для высокорисковой заявки)

Порог «Скоринг <600» взят из АР МСБ §2.2 и АР HITL
